# AlchemyEngine — ビジョンと設計思想

## このドキュメントの目的

AlchemyEngine が「何を保証するか」「何を保証しないか」を明文化する。
これはコードの設計判断の拠り所であり、機能追加・リファクタリング・新しいコンテンツを作るときに立ち返るべき原則を定義する。

---

## 一言で言うと

> **AlchemyEngine は、単精度の仮想空間の状態をサーバーが持ち、複数のユーザーが参加できるVRプラットフォームです。**
> **仮想空間上のコンテンツはユーザーが持ち寄り、リアルタイムに編集し決めます。**

サーバーが単精度の仮想空間の状態を持つ間隔を権威 tick、重い数式だけを預ける実行器を Formula VM、その単精度を binary32（32ビット浮動小数）と呼ぶ。それぞれ何を含み、何を含まないかは次の表に書く。

---

## 2つの概念の定義

### Engine（エンジン）— AlchemyEngine が保証するもの

エンジンが提供するのは、あらゆるコンテンツの「器」となる基盤だけだ。
保証として書く行は、現行のコードが果たしている契約に限る。

| いま保証するもの | 説明 |
|---|---|
| **ユーザーの参加** | 複数のユーザーが仮想空間に入り、サーバーが持つその仮想空間の状態を受け取り、抜けられる。そのユーザーの位置と向きの計算は、エンジンの器としては持たない |
| **権威 tick** | **主時間は Elixir**（推奨 **20Hz**。設定で 10 / 20 / 30Hz、および非推奨の 60Hz）。クライアント描画は別時間（既定 ~60fps）で予測・補間する。旧「Rust 60Hz 物理ループ」は撤去済み |
| **Formula VM** | サーバー NIF は `run_formula_bytecode` のみ。重い式のオフロードであり、ゲームルールは持たない |
| **単精度の仮想空間** | サーバーが持つ状態と、共有する座標は binary32（`protocol` の `float`、クライアントの `f32`）。Elixir プロセス内の float が binary64 であることは、仮想空間を共有する契約ではない |
| **フレーム配送** | 複数のユーザーが同じ仮想空間のフレームを受け取る同期の器 |
| **描画の器** | 受け取ったフレームを画面に映す仕組み |
| **コンポーネントのライフサイクル** | `on_ready` / `on_process` / `on_physics_process` / `on_event` の呼び出しタイミング |

| まだ保証しないもの | 説明 |
|---|---|
| **binary64 の共有 3D 座標系** | 単一原点の binary64 を、仮想空間の共有契約にはしていない。浮動原点は別作業 |
| **物理の器** | 衝突判定・空間分割・移動はエンジンの器としては無い。当たり判定はコンテンツが持つ。Elixir 側の物理の器は別作業 |
| **3D 空間オーディオ・DSP** | 空間オーディオと DSP をエンジンの基盤としては保証しない |

エンジンは「敵」「武器」「EXP」「スコア」「ボス」「レベル」「地形」「スカイボックス」を知らない。
これらはすべてコンテンツであり、ユーザーが持ち寄り、リアルタイムに編集し決めるものだ。

### Content（コンテンツ）— ユーザーが持ち寄り、リアルタイムに編集し決めるもの

コンテンツは**コンポーネントの集合**だ。

エンジンの上に乗るものはすべてコンテンツであり、コンテンツはコンポーネントで構成される。
「ワールド（仮想空間の見た目・地形）」も「ルール（ゲームロジック）」も、どちらもコンポーネントの一種に過ぎない。

```
Content = [ComponentA, ComponentB, ComponentC, ...]
```

各コンポーネントはエンジンのライフサイクルに応答する：

```elixir
defmodule GameEngine.Component do
  @optional_callbacks [on_ready: 1, on_process: 1, on_physics_process: 1, on_event: 2]

  @callback on_ready(world_ref)          :: :ok  # 初期化時（1回）
  @callback on_process(context)          :: :ok  # 毎フレーム（Elixir側）
  @callback on_physics_process(context)  :: :ok  # 論理上の「物理」ステップ（呼び出し間隔は実装依存）
  @callback on_event(event, context)     :: :ok  # イベント発生時
end
```

これは Unity の `MonoBehaviour`、Unreal の `ActorComponent`、Godot の `Node` と同じ思想だ。
エンジンはコンポーネントの「中身」を知らない。ライフサイクルのタイミングだけを提供する。

## Elixir と Rust の責務と時間

実装層では、**Elixir（contents）** と **Rust** が明確に役割を分担する。
**主時間（権威のある論理時間）は Elixir 側**に置く。詳細な Hz 区分は [authoritative-state-sync-policy.md](architecture/authoritative-state-sync-policy.md) を正本とする。

### 責務の分担

| レイヤー | 責務 |
|:---|:---|
| **Elixir（contents）** | **ドメインの SSoT**。権威ある状態・ルール・コンテンツ定義・公式 tick。「何が起きたか」を決める |
| **Rust（クライアント）** | **表示・体感の補完**。描画・入力キャプチャ・DSP・予測・補間。「どう見えるか」を滑らかにする。公式状態の真実にはならない |
| **Rust（サーバー NIF）** | **Formula VM**（`run_formula_bytecode`）のみ。重い式のオフロード。ゲーム用物理ループはない |

Elixir は **コンテンツとゲームルール**における **SSoT（Single Source of Truth）** である。Rust クライアントは権威 tick の間を埋める表示層であり、旧来の「サーバー物理の実行層」ではない。

**別の「真実」として**、Elixir サーバーと Rust クライアント等が **同じバイト列**で合意する **Protobuf メッセージ**（例: Zenoh の `RenderFrame`）は **`proto/*.proto`** をその形式のワイヤ契約の SSoT とする。UDP 外枠や WebSocket の JSON など **別形式**は別のモジュール／文書が契約の SSoT になる。ドメインの判断は Elixir、Protobuf のフィールド番号・型は `.proto`、という整理に分ける（詳細は [architecture/overview.md](architecture/overview.md#設計思想)）。

**コンテンツ固有のスキーマ・ルール・パラメータは Elixir の `apps/contents` が持つ。** クライアントは受け取った定義・フレームに従って描画・補間する。

### 主時間と表示時間

| 時間 | 担い手 | 意味 |
|:---|:---|:---|
| **主時間（権威 tick）** | **Elixir** | 公式状態のコミット間隔。**推奨 20Hz**。ユーザー／運用設定で **10 / 20 / 30Hz**、および **非推奨の 60Hz** まで選択可能（[authoritative-state-sync-policy.md](architecture/authoritative-state-sync-policy.md)） |
| **表示時間** | **Rust クライアント** | 描画・入力・オーディオのパイプライン（既定 ~60fps）。主時間のスナップショットを **予測・補間**で滑らかにする。主時間を置き換えない |

- ゲーム用の **60Hz `GameWorld` 物理ループ NIF は廃止**（2026-04 時点）。
- コンテンツとネイティブの橋渡しは、プロトコル化されたフレーム（protobuf）・イベントタプル（後方互換の `{:frame_events, ...}` 等）・Formula 呼び出しで行う。

## Hub — コンテンツを公開する場所

ユーザーが持ち寄ったコンテンツは **Hub** にパブリッシュされる。
ユーザーは Hub から好きなコンテンツを選び、ダウンロードして遊ぶ。

```
ユーザーA: BulletHell3D コンテンツ → Hub
ユーザーB: FormulaTest コンテンツ  → Hub
ユーザーC: CanvasTest コンテンツ   → Hub
```

Hub 自体もエンジンが動かす一つのコンテンツだ。
ロビー、アバター選択、コンテンツ選択画面も、仮想空間上に存在する。

## 複数ユーザーの保証とネットワーク基盤

仮想空間で複数のユーザーが同時に遊ぶとき、エンジンは以下を保証する設計思想を持つ。

### バックプレッシャー設計

**バックプレッシャー**とは、処理の速い側が遅い側に追いつかれないよう、送信・生成を抑制する仕組みである。
水道管に例えると、排水が追いつかなければ蛇口を絞る——その「圧力を戻す」思想だ。

| 保証しないとどうなるか | 保証するとどうなるか |
|---|---|
| メッセージキューが際限なく増える | キュー長を抑制し、リソース枯渇を防ぐ |
| 送信側が受け手の処理能力を超えてしまう | 受け手の処理速度に合わせて流れを制御する |
| 遅延が増大し、システム全体が不安定になる | 負荷が高くてもシステムは安定して応答する |

この思想は OTP（Erlang VM）や Phoenix LiveView と同様である。
OTP のメッセージパッシングでは、`GenServer.call` による同期呼び出しや有界キューを用いて、
送信側が受け手の処理能力を超えないよう設計する。
LiveView は WebSocket 経由でクライアントへ状態を送る際、クライアントの受信速度に合わせる形でバックプレッシャーを組み込んでいる。

**AlchemyEngine もこの思想を取り入れる。**
多数のユーザーが同じ仮想空間を共有するとき、サーバーからクライアントへ、あるいはプロセス間で送るデータ量は、
受け手の処理能力に合わせて制御されることを保証する設計とする。

### 複数ユーザー同時参加時の保証

| いま保証するもの | 説明 |
|---|---|
| **権威状態の配送** | 同じ仮想空間のユーザーは、Elixir の権威 tick がコミットしたフレームを受け取る |
| **バックプレッシャー** | 送信側が受け手の処理能力を超えてキューを膨らませないよう、流れを制御する設計とする |
| **参加・離脱のライフサイクル** | ユーザーの参加・離脱を検知し、仮想空間内の状態を更新する |

コンテンツ固有の「敵の出現パターン」「武器のバランス」は保証しない。
これらはユーザーが持ち寄り、リアルタイムに編集し決める責務である。

### 同期の仕組み

複数のユーザーが同じ仮想空間を共有する際の同期は、以下の層で設計する。

| 層 | 責務 |
|---|---|
| **イベントの伝播** | ゲームイベント（参加・離脱・コンテンツ固有イベント）を、必要なユーザーに届ける |
| **状態の配送** | クライアントへ送る状態更新を、バックプレッシャーを考慮した配送経路で行う |

同期の単位は**仮想空間**である。
同じ仮想空間に参加するユーザーは、その仮想空間の権威 tick がコミットした状態とイベントを共有する。
仮想空間ごとに GenServer または相当するプロセスを持ち、そのプロセスのメールボックスとメッセージ設計がバックプレッシャーを実現する。

物理演算結果（位置・速度・衝突）をユーザー間で一貫させることは、現行の保証ではない。目指す姿に置く。

## 現在地と目指す場所

### 現在（2026-04 時点）

```
Engine ← Formula NIF（run_formula_bytecode）+ 描画・ネットワーク・クライアント（Rust 他）
Content ← CanvasTest / BulletHell3D / FormulaTest 等（コンポーネント群）
```

`config :server, :current` でコンテンツモジュールを指定する（例: `Content.BulletHell3D`）。

ゲーム用 Rust `GameWorld` / `physics_step` ループは **ない**。バランス・ルールの SSoT は Elixir（contents）を正とし、必要な数式は Formula バイトコードで実行する。

### 目指す姿

次は到達点であり、現行の保証ではない。

- ワイヤを越える binary64 の共有座標系（浮動原点）
- 衝突・空間分割・移動を担う物理の器
- 3D 空間オーディオと DSP
- 物理演算結果（位置・速度・衝突）をユーザー間で一貫させる同期
- Hub での一覧・選択・参加

```
Engine  ← 上の到達点を含む器・ネットワーク基盤・コンポーネントライフサイクル
Content ← ユーザーが持ち寄り、リアルタイムに編集し決めるコンポーネント群
Hub     ← コンテンツの一覧・選択・参加
```

#### 空のコンテンツが成立する

コンテンツの最小形は `{}` だ。

```json
{}
```

これだけで仮想空間は存在し、ユーザーはその仮想空間に入ることができる。
「何もない仮想空間に立つ」という体験が、エンジンが保証する最低限の約束だ。

コンポーネントはその後から追加される。
地面を置く、光を置く、敵を置く——それはすべてユーザーの選択であり、
エンジンはその選択を強制しない。

#### コンポーネントはリアルタイムに編集できる

コンテンツ定義（コンポーネントの集合）はランタイムに変更できる。
ユーザーがコンポーネントを追加・変更・削除すると、
ユーザーが入っている仮想空間がリアルタイムに変化する。

```
ユーザーが編集                  ユーザーが体験
  {} → {ground: ...}    →    地面が現れる
  {} → {enemy: ...}     →    敵が現れる
  {} → {sky: ...}       →    空が変わる
```

これは「ゲームを作ってから遊ぶ」ではなく、
**「作りながら遊ぶ」** という新しい体験の形だ。

## 設計判断の原則

機能追加やリファクタリングの際は、以下の問いに答えること。

**「これはエンジンの責務か？」**
→ 「どんなコンテンツにも必要か？」と問い直す。
→ 特定のサンプルコンテンツにしか必要でないなら、エンジンに置かない。

**「エンジンはこの概念を知る必要があるか？」**
→ エンジンが知るべきは「エンティティが存在する」という事実だけ。
→ そのエンティティが「敵」か「NPC」かはコンポーネントが決める。

**「これはコンポーネントに分解できるか？」**
→ 単一責務のコンポーネントに分解できるなら、そうする。
→ コンポーネントは `on_ready` / `on_process` / `on_physics_process` / `on_event` のうち必要なものだけ実装する。

## 現在の実装との対応

### Elixir 側

| モジュール | 位置づけ |
|---|---|
| `Contents.SceneBehaviour` | シーンインターフェース（contents） |
| `Contents.Events.Game` | ルーム単位のイベントディスパッチ・コンポーネントライフサイクル |
| `Core.ContentBehaviour` / `Core.Component` | コンテンツ・コンポーネントの契約 |
| `Content.*`（例: `Content.BulletHell3D`） | コンテンツ実装（`config :server, :current`） |

旧 `WorldBehaviour` / `RuleBehaviour` / `GameContent.*` 系は **廃止またはコンテンツ側へ統合済み** の場合がある。詳細は [architecture/overview.md](architecture/overview.md)。

### Rust 側（2026-04）

| コード | 位置づけ |
|---|---|
| `rust/nif` | Formula VM の **`run_formula_bytecode`** のみ（ゲーム用 `GameWorld` NIF は撤去済み） |
| `rust/client/render` / `rust/client/app` / `rust/client/network` | 描画・クライアント・プロトコルデコード |
| 旧 `native/nif` 内 `physics` / `GameWorld` | **アーカイブ**（ドキュメントのみ残る場合あり） |

## 移行の完了状況（抜粋）

1. ✅ **ゲーム用 Rust NIF（`GameWorld`・60Hz ループ）は撤去**（2026-04）。メインループは Elixir（contents）。
2. ✅ **`Contents.Events.Game` へのイベント層集約**（旧 `game_events`）。
3. ✅ **Formula NIF に一本化**（`Core.NifBridge.run_formula_bytecode`）。
4. 未実装・継続課題は [architecture/overview.md](architecture/overview.md) および improvement-plan を参照。
