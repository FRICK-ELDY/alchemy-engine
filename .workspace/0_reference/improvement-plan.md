## 第 1 波

### P-1: ネットワーク由来の終了をノード停止から外す

**問題**: `"__quit__"` は既定の UI アクションで、`Events.Game` が `System.stop(0)` に到達する。既定コンテンツの Quit ボタンも同じ文字列を送る。`handle_info` に受け皿がなく、非 binary の action でプロセスが落ちる。落ちた `:main` は `RoomSupervisor` 再起動後に戻らない。

**方針**: リモート入力から呼べる action を許可リストにする。ノード停止はローカルの開発操作に限る。`handle_info` の末尾で未知メッセージをログして `:noreply` する。`:main` は supervisor の再起動で再生成する。

**対象**: `world-server/apps/contents/lib/components/category/device/keyboard.ex`, `world-server/apps/contents/lib/events/game.ex`, `world-server/apps/contents/lib/contents/sample_osc.ex`, `world-server/apps/server/lib/server/application.ex`

**消える点数**: `__quit__` -4、受け皿欠如 -3、`:main` 非復元 -2。合計 **-9**。

### P-2: クライアントテストを CI で実行する

**問題**: `client` のワークフローに `cargo test` がない。`SnapshotInterpolator` の 18 件を含むテストが回帰を止めていない。

**方針**: `cargo test --workspace` を client CI に足す。GPU 依存で落ちるクレートがある場合は除外理由をワークフローに書く。件数の 52 と 61 の差は、CI が数えた数を正とする。

**対象**: `client/.github/workflows/ci.yml`

**消える点数**: クライアントテスト未実行 **-3**。

### P-3: 保証文を実装に合わせる

**問題**: `vision.md` は binary64 の 3D 座標と物理の基盤を保証している。ワイヤと描画は f32 で、物理クレートは無い。`.workspace/0_docs/warranty/ci.md` は分割前の physics ジョブとルート CI を説明している。評価ルールの physics 節も現行ツリーとずれる。

**方針**: いま保証しているもの（権威 tick、f32 の描画契約、Formula VM）と、まだ保証していないもの（binary64、物理、3D オーディオ）を表で分ける。実装に進むなら提案一覧の浮動原点と Elixir 側の物理の器を別作業にする。文書の書き換えだけで -4 と -3 と保証文書 -3 は消える。実装は消えない点数を新たに生まない範囲で計画する。

**対象**: `.workspace/0_docs/vision.md`, `.workspace/0_docs/warranty/ci.md`, `.cursor/rules/evaluation.mdc`

**消える点数**: binary64 -4、物理の保証不一致 -3、保証文書 -3。合計 **-10**。

### P-4: 認証を入室経路まで繋ぐ

**問題**: `AUTH_REQUIRED` は既定 false。`RoomToken` に `sub` がない。公式クライアントはトークンを付けないので、認証をオンにすると遊べない。

**方針**: 本番の既定をオンにし、未設定の JWKS では起動しない（検証器は既にある）。RoomToken に `sub` を入れ、クライアントはキーリングのトークンから RoomToken を得て envelope に載せる。開発用の無認証は明示フラグに限る。

**対象**: `world-server/config/config.exs`, `world-server/apps/network/lib/network/room_token.ex`, `client/network`, `client/app`

**消える点数**: 既定オフ -3、`sub` なし -3、入室不能 -4。合計 **-10**。

第 1 波の合計は **-32**（P-1 の -9、P-2 の -3、P-3 の -10、P-4 の -10）。

## 第 2 波

### P-5: シーンスタックをルームの子にする

**問題**: tick はルーム単位で、`Contents.Scenes.Stack` は 1 つである。`flow_runner/1` が `room_id` を捨てる。

**方針**: `scene_stack_spec/1` を実装し、ルームの子プロセスとしてスタックを起動する。2 ルームが互いのスコアとシーンを上書きしないテストを足す。

**対象**: `world-server/apps/server/lib/server/application.ex`, `world-server/apps/contents`

**消える点数**: シーン共有 **-4**。`Device.Helpers` の `:main` 固定 -1 もここで直す。

### P-6: サーバ側 Zenoh を再接続する

**問題**: クライアントは指数バックオフで戻る。サーバの購読は戻らない。

**方針**: セッションの死活を見て、購読を張り直す。クライアント側の generation と同じく、古いセッションのコールバックを捨てる。

**対象**: `world-server/apps/network/lib/network/zenoh_bridge.ex`

**消える点数**: **-3**。

### P-7: UDP の契約と入口上限

**問題**: 信頼性、リプレイ、断片化が無く、パケット長・セッション数・頻度の上限も無い。

**方針**: 上限を先に入れる。信頼性を自前で足すか、提案の QUIC / WebTransport に寄せるかは上限のあとで決める。全ノード RPC と平文 S2S は、探索結果のキャッシュと https 限定として同じ変更に含めてよい。

**対象**: `world-server/apps/network`

**消える点数**: UDP 契約 -3、入口上限 -2、RPC スキャン -2、平文 HTTP -1。合計 **-8**。

### P-8: Formula VM に実行上限を置く

**問題**: ユーザー定義バイトコードが通常スケジューラで、命令数と入力サイズの上限なく走る。

**方針**: バイト数と命令数で打ち切り、DirtyCpu へ移す。エラーの返し方をタプルに揃える。

**対象**: `world-server/rust/nif`

**消える点数**: 上限なし -3、エラー分類の揺れ -1、ABI の弱さ -2 のうち上限とエラー分類まで。ABI バージョンそのものは P-14 に残すと **-4** がここから消える（-3 と -1）。ABI -2 は P-14。

### P-9: 描画対応を安定 ID にし、予測の入口を作る

**問題**: 補間が最近傍で、予測は恒等関数。`RenderFrame` の毎フレーム clone、カリングなし、render の回帰テストなしが残る。

**方針**: protocol に安定 ID を足し、最近傍をやめる。自機予測は提案側の本実装でも、恒等関数であることはコメントとテストで明示して -2 を「未実装であることが契約」に変える。headless の 1 枚を golden にする作業は提案一覧に従う。

**対象**: `protocol`, `client/shared`, `client/render`

**消える点数**: 最近傍 -3。予測 -2 は入口を作った時点では残し、reconciliation まで入れて消す。

### P-10: メール検証を発行条件にする

**問題**: 検証フローと行ロックはある。未検証でも access / refresh が出る。リフレッシュのローテーションに競合がある。

**方針**: 未検証ユーザーにはトークンを出さない。ローテーションは 1 トランザクションで旧トークンの無効化と新トークンの挿入を行う。

**対象**: `auth-server/lib/auth`

**消える点数**: 未検証発行 -3、ローテーション競合 -2。合計 **-5**。

## 第 3 波

### P-11: スーパープロジェクトで横断検証する

**問題**: ピンの不一致、golden の片側更新、認証付き smoke を見る CI がない。`mix alchemy.ci` は world-server だけを見る。起動手順は `.bat` 前提。前回計画が止まった記録は、この入口が無いこととセットである。

**方針**: スーパープロジェクトに、ピン一致、client `cargo test`、world-server と auth-server のテスト、認証オンの smoke を 1 ワークフローで置く。ローカルは `mix alchemy.ci` をルートから子へ委譲するか、doctor コマンド（提案）で代替する。

**消える点数**: 横断検証 -3、`alchemy.ci` の範囲 -2、`.bat` 前提 -1、改善サイクル停止 -2。合計 **-8**。

### P-12: 残りのネットワーク境界

**問題**: 封筒形式の推測、health がルーム ID を返す、Zenoh のヒューリスティック。

**方針**: 封筒はバージョンフィールドで分岐する。health は生存だけを返す。

**消える点数**: 封筒 -1、health のルーム ID -1。合計 **-2**。

### P-13: 永続化を 1 本通す。Tetris を dt 化する

**問題**: save / load はログのみ。Hub と編集は経路になっていない。Tetris だけ 60Hz 固定。スタブと未登録コンポーネント、武器・ボスの未実装コールバック、カタログコメントの不一致が残る。

**方針**: `__save__` / `__load__` を、1 コンテンツで実際の状態へ接続する。Tetris の落下を `context.dt` にする。未実装コールバックは消すか、実装するコンテンツを 1 つに限る。

**消える点数**: save/load -3、Hub 経路 -2、Tetris -2、スタブ -2、コールバック -1、カタログ不一致 -1。合計 **-11**。

### P-14: core と NIF の契約を現状に合わせる

**問題**: `NifBridge.Behaviour` が未配線。`FormulaStore` の ETS 所有者が不定。ABI バージョンが弱い。除算に偏ったテスト。撤去済み語彙と旧パス。`contents` の `network` 依存。

**方針**: Behaviour をブリッジに接続し、ETS のオーナーをプロセスにする。語彙の掃除はテストで「core が敵やボスのキーを持たない」ことを固定する。

**消える点数**: Behaviour -2、ETS -2、ABI -2、除算偏り -1、語彙 -2、contents→network -1。合計 **-10**。

### P-15: 配布単位と server のテスト

**問題**: world-server に release が無い。server の専用テストが無い。`ASSETS_ID` の `put_env`。CI は Linux のみで、クライアントの配布が無い。依存監査が無い。分割の残骸が残る。

**方針**: world-server の release を auth-server の Dockerfile と同じ粒度で置く。`mix audit` と `cargo audit`（または cargo-deny）を各リポジトリの CI に足す。OS 行列は client のビルドから。

**消える点数**: release -2、server テスト -1、`ASSETS_ID` -1、監査 -2、単一 OS / 配布 -2、残骸 -1。合計 **-9**。

### P-16: 観測と失敗の分類

**問題**: telemetry が ConsoleReporter に留まる。重要失敗を黙って捨てる経路がある。プロパティテストと fuzz とベンチが無い。

**方針**: フレームドロップ、再接続、認証拒否にイベント名を付け、リポータを差し替え可能にする。未知入力は drop か crash かを 1 表に書く。プロパティテストは P-8 の VM と protocol から 1 本でよい。

**消える点数**: telemetry -2、黙って捨てる -2、プロパティ欠如 -2。合計 **-6**。

### P-17: クライアントの残件

**問題**: WASM は空。network クレートが描画と音声に依存する。セッションエラーが文字列一致。移動を毎フレーム publish する。ウィンドウ初期化が panic する。音声の同時発音に上限がない。OpenXR が出荷 app に無い。`RenderFrame` の clone。カリングが無い。render の回帰が無い。

**方針**: OpenXR は出荷メニューに出すか、クレートを実験であると文書で切る。出さないなら -3 は P-3 の書き分けで消してよい。WASM は「未対応」を型で表し、常時エラーのスタブをやめる。音声は同時発音の上限だけ先に入れる。

**消える点数**: WASM -2、クレート依存 -1、文字列エラー -1、無条件 publish -1、panic -1、音声上限 -2、OpenXR -3、clone -1、カリング -1、render 回帰 -2。合計 **-15**。予測 -2 は P-9 に残る。

### P-18: コンテンツの厚み

**問題**: 完結したゲームは 2 本。アセットが薄い。これはエンジンの欠陥というより、デモが技術検証のまま止まっていることである。

**方針**: 新しいゲームを増やさない。既存 2 本の見た目と音を、パラメータの外側から差し替えられることだけ確認する。量産は本計画の完了条件にしない。

**消える点数**: ゲーム本数 -2、アセット -2。合計 **-4**。優先度は最下位でよい。

### P-19: auth-server の運用境界

**問題**: 最低年齢が無い。`account_tokens` の GC が無い。レート制限が単一ノード ETS。health が DB を見ない。CORS が無い。LiveView socket が残る。

**方針**: health に DB 照会を足す。CORS は許可リストにする。LiveView の入口は API サービスから外す。年齢と GC とレート制限の分散は、複数ノードに載せる前でよい。

**消える点数**: 年齢 -1、GC -1、レート制限 -1、health -1、CORS -1、LiveView -1。合計 **-6**。
