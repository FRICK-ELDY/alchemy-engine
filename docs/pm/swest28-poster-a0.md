## ヘッダー

**分散連合型VRプラットフォームの開発と研究**  
Development and Research of a Distributed Federated VR Platform

FRICK-LAB 松尾 英樹

---

## 左上 — 概要

本研究では、個人や組織が自分のドメインで VR 空間を運営し、インスタンス同士が連合できる **分散連合型 VR プラットフォーム AlchemyEngine** の開発と研究について報告する。

AlchemyEngine は、エンジンが保証するものを **「無限の3D空間」** と **「そこに存在するユーザー」** に限定する。空間の上に何を置くかはすべて **コンテンツ** であり、利用者がコンポーネントとして持ち込む。空間の正しい状態は **サーバー（Elixir）** が決め、描画と入力は **Rust クライアント** が担う。

---

## 左下 — 方法・アーキテクチャ

### 起動構成

```
zenohd → サーバー（Elixir） → クライアント（Rust）
         mix alchemy.router   mix alchemy.server   mix alchemy.client
```

### サーバー（Elixir Umbrella）

| アプリ | 役割 |
|:---|:---|
| `contents` | 時間の進行・シーン・コンポーネント |
| `core` | 設定・Formula VM 橋渡し |
| `network` | Zenoh 送受信 |

- 各空間は **OTP プロセス** として隔離
- 重い計算は **Rust NIF（Formula VM）** へオフロード
- 認証は別サービス **alchemy-auth** が担当

### クライアント（Rust）

- 描画: **wgpu / winit**（~60 fps）
- 通信: **Zenoh** + **Protobuf**（alchemy-protocol）
- 入力 → サーバー → 空間の状態 → クライアント描画

### データフロー

1. `contents` が空間の状態を Protobuf 化 → `network` が Zenoh で送信
2. クライアントが受信・描画
3. 入力を Zenoh でサーバーへ返送 → 空間に反映

## 右上 — 背景・課題

### 既存 VR プラットフォームの限界

- 単一運営者による **閉じたサービス** が主流
- 特定エンジン前提の実装が多い
- 誰でも自分の空間を持ち、他と繋がる形になりにくい

### テキスト SNS との対比

| | Mastodon / Misskey | AlchemyEngine（目指す姿） |
|:---|:---|:---|
| ホスト | セルフホスト可能 | セルフホスト可能 |
| 連合 | ActivityPub | 合意プロトコル（将来） |
| 空間 | テキスト | **3D 空間 + リアルタイム同期** |

3D 空間とリアルタイム同期を対象にした分散連合基盤は **まだ少ない**。

## 右中 — 結果

Elixir サーバーと Rust クライアントを分けた構成で、**3D 空間の状態をリアルタイムに同期** できることを確認した。

- サーバーが進めた状態を **Protobuf フレーム** として Zenoh 送信 → クライアントが描画
- キーボード入力も Zenoh でサーバーへ返送 → 空間に反映
- エンジンはコンテンツの中身を知らず、**コンポーネントのライフサイクル**（`on_ready` / `on_process` / `on_event`）に応答する分離を実装

**示されたこと**: 自前ホスト可能な VR 空間の基盤を、エンジンとコンテンツの境界として定義できる。

---

## 右下 — 結論・参考文献

### 結論

分散連合型 VR プラットフォームの基盤として、Elixir/OTP のプロセス分離と Rust クライアントによる描画分離が有効であることを示した。今後は **インスタンス間連合** の実装と、教育・共同作業への応用を目指す。
