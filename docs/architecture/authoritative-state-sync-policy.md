## 1. Single Source of Truth（SSOT）の三層

マルチプレイで一貫性を説明するとき、次の三つに分ける。


| 層                   | 責務                           | 主な担い手                                          |
| ------------------- | ---------------------------- | ---------------------------------------------- |
| **状態の SSOT**        | 公式の世界状態（確定したエンティティ・ルール・スコア等） | **Elixir サーバー**                                |
| **入力のキャプチャ／ローカル意図** | デバイスからの取得・正規化・送信の起点          | **Rust クライアント**                                |
| **公式に適用される入力列**     | 順序・採否・検証後にシミュレーションに入るコマンド列   | **サーバー側で確定**（Elixir、または **Elixir が信頼する一本の経路**） |

上表の **「状態の SSOT」** は **ゲーム世界の公式な中身** の話である。**メッセージをバイト列や JSON としてどう符号化するか** の **ワイヤ契約**は別レイヤーで、**経路・形式ごとに** SSoT の置き場が異なる（例: **Protobuf ペイロード**は **`proto/*.proto`**、UDP 外枠は **`Network.UDP.Protocol`**、Phoenix はチャネルごとの JSON 仕様）。整理は [overview.md](./overview.md#設計思想) の「二層の SSoT」表を参照。

クライアントは信頼できないため、「クライアントが送った内容＝無条件に真実」とはしない。**採用された入力の順序**はサーバーが宣言する。

**確定フレーム**（公式にコミットするタイムステップの区切り）は **Elixir** が行う。クライアント側の予測・補間や入力キャプチャが 60Hz でも、**権威ある状態のコミット**は Elixir の主時間に収束させる。

---

## 2. 主時間（何の Hz を正とするか）

**AlchemyEngine の主時間は Elixir の権威 tick である。**

- 公式の「何が起きたか」は、この tick でコミットされた状態だけが正である。
- Rust クライアントの描画ループ（既定 ~60fps）は **表示時間**であり、主時間のスナップショットを予測・補間で埋める。表示時間は主時間を置き換えない。
- サーバー NIF にゲーム用 60Hz 物理ループはない（Formula VM のみ）。

Hz を議論するときは、次節のとおり **権威 / 描画 / ネットワーク** を混同しない。

---

## 3. 更新レートの区分

### 3.1 権威サーバー（Elixir）の tick — 主時間

Elixir は計算集約の高頻度ループには向かない。**公式状態の進行 tick** はユーザー／運用設定で選べる。


| モード | Hz | 用途 |
| --- | --- | --- |
| 低速 | **10** | テスト・プロファイリング・低負荷 |
| **推奨（デフォルト）** | **20** | 通常運用の想定 |
| 高速 | **30** | 遅延低減が必要な場合 |
| 上限（**非推奨**） | **60** | 特例・実験。BEAM 負荷・キュー詰まりリスクが高い |


- **デフォルトは 20Hz** とする。
- **10 / 20 / 30 / 60** を設定可能にする（UI・config・ルーム設定のいずれか。実装は段階的でよい）。
- **60Hz は非推奨**。ハードリアルタイム保証はしない（GC・スケジューリング揺らぎがある）。選んでも「厳密な 16.67ms」は約束しない。
- ネットワーク上でクライアントが「公式」とみなす状態更新の周期は、原則としてこの **Elixir tick** に従う。

### 3.2 クライアント描画フレームレート — 表示時間

- **ユーザー設定**可能にする。
- **デフォルト**は端末スペックに応じて **30 FPS または 60 FPS** を推奨。
- **上限**は利用ディスプレイ（**VR では HMD の表示モード**を含む）のリフレッシュレートに合わせる。
- 描画 Hz は体験品質の話であり、**権威 tick と独立**してよい。
- 権威 tick が 10〜30Hz（または非推奨 60Hz）でも、描画側は **予測・補間**で滑らかさを担う（[rust_client.md](../policy-as-code/rust_client.md)、[render-interpolation.md](../policy/render-interpolation.md)）。

### 3.3 入力キャプチャ

- デバイスからの入力サンプリングはクライアント側の表示ループに寄せてよい（高頻度キャプチャ）。
- **公式への適用・採否・順序付け**は Elixir の権威 tick 側で行う。入力にシーケンス番号等を付け、サーバが ack／確定する契約を崩さない。

### 3.4 ネットワーク

- **低遅延**を優先。Zenoh・protobuf（`render_frame.proto` 等）の利用はその一環。
- 配信レートは原則 **権威 tick に揃える**（「60Hz フルフレーム必須」ではない）。
- プロバイダ契約 Mbps だけでなく、**アプリ実測**（送受バイト／秒、損失、RTT）を取得・記録し、品質プリセットや UI に反映する。**ユーザーごとの目標帯域を保証する**のではなく、**計測と把握**を主とする。

## 4. 可視範囲・同時可視（インタレスト管理）

- **距離カット・同時可視人数の上限**などは、**クライアントが調整**可能にする（PC スペック依存が大きいため）。
- **デフォルト**はクライアントがハードウェアを検出し、**自動推奨**する。

将来、不正や過負荷対策として **サーバー側のハードキャップ**を設けるかは別途検討可能。

---

## 5. 権限（ロール）と権威

権限階層の例:

`admin` > `builder` > `moderator` > `guest` > `spectator`

- **権威の複製（P2P で各自が正）**ではなく、**サーバー上のポリシー（RBAC）**として実装する。
- ロールは **サーバー側で毎回検証**する。クライアントの主張は信じない。
- `builder` 等の「権威」は、**サーバーがその操作を受理し状態を更新する**能力の意味合い。

---

## 6. リモートコンテンツの配布

- **改ざん・盗聴・なりすまし**を優先し、当面は **HTTPS ＋ 署名**（マニフェスト／ハッシュと作者または Hub の署名）を妥当な第一選択とする。
- 将来、転送経路だけ P2P 化する場合も、**同一の信頼の鎖（署名・コンテンツアドレス）** と両立させる。

---

## 7. 同時接続・パフォーマンス保証について

- **公式にサポートする同時人数・更新品質**は、**ホストマシンの CPU／メモリ**およびネットワーク条件に依存する。
- **ベンチマークとレポート**を経て数値目標を宣言する。

参考としての個人目標（未検証）:

- 既存サービスが許容するインスタンス規模（例: 数十人規模）を超える **同一空間の同時存在人数**（例として **255 人**）を視野に入れる。
- ただし **「全員フル同期・全員が互いにフル解像度」** と **描画 Hz／権威 tick／ネット更新 Hz** は別問題であり、**興味管理・間引き・LOD** とセットで定義する。

詳細なスケール上のギャップは [scale-and-gaps.md](../policy-as-code/gaps/scale-and-gaps.md) を参照。
