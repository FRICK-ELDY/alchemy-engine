# Policy: Elixir — 責務・禁止事項

[← index](./index.md)

> **Elixir の得意分野**: Actor モデルによる並行処理・メッセージパッシング・障害耐性。軽量プロセスを大量に扱い、分散システムや I/O バウンドな処理に向く。連続的な重い数値演算には不向き。
>
> **補足（I/O バウンド）**: 入出力待ちで処理時間の大半が消費される状態。ネットワーク・DB・ディスクなどへの待ちが主となる。CPU バウンド（演算に時間がかかる）とは対照的で、Elixir は前者に適し、重い式は Formula VM（Rust NIF）に向く。

> **2026-07-23 更新**: **主時間は Elixir の権威 tick**（推奨 **20Hz**。設定で 10 / 30 / 非推奨 60Hz）。クライアント描画は別時間（予測・補間）。正本は [authoritative-state-sync-policy.md](../architecture/authoritative-state-sync-policy.md)。旧「サーバー Rust 60Hz `GameWorld` ループ」はない。

---

## 1. 主時間は Elixir。ハードリアルタイムの 60Hz 保証はしない

**やってはいけないこと**: BEAM 上で **厳密な** 60Hz（約 16.67ms 毎）の**ハードリアルタイム**を保証できると仮定すること。デフォルトを 60Hz にすること。

**理由**:

- メッセージ配送・スケジューリング・GC の揺らぎがあり、フレーム間隔は一定にならない
- 多数ルーム・多数プレイヤー時に、過度に高い刻みを要求するとキュー詰まりやスケジューラ圧迫のリスクが高まる
- クライアントの描画（約 60fps）は **表示時間**であり、主時間（権威 tick）とは別物

**やるべきこと**:

- **主時間（権威 tick）** を Elixir タイマーで回す
- **デフォルト 20Hz**。ユーザー／運用設定で **10 / 20 / 30Hz**、および **非推奨の 60Hz** を選べるようにする
- 遅延やスキップを設計に組み込む（バックプレッシャー等）
- 数式の重い部分は **Formula VM**（`run_formula_bytecode`）へ
- 見た目の滑らかさはクライアント側の **予測・補間**に任せる（[rust_client.md](./rust_client.md)）

| レート | 位置づけ |
|:---|:---|
| 10Hz | 設定可。テスト・低負荷 |
| **20Hz** | **推奨・デフォルト（主時間の基準）** |
| 30Hz | 設定可。遅延低減向け |
| 60Hz | 設定可だが **非推奨**。ハード RT 保証なし |

## 2. 責務の逆転をしない（Elixir はドメイン SSoT・主時間）

**やってはいけないこと**: クライアントの予測結果や描画状態を公式真実にすること。Rust がゲームルールの定義を持つこと。サーバー側にゲーム用 60Hz 物理ループを再導入すること。

**理由**:

- **Elixir**: **ドメイン**における定義と権威 tick の SSoT。「何を・どうするか」「何が確定したか」を決める
- **`.proto`**: **Protobuf を使うペイロード**について、Elixir と Rust が同じバイト列で合意する **フィールド契約**の SSoT（[architecture/overview.md](../architecture/overview.md#設計思想)）
- **Rust クライアント**: 権威スナップショットを受け取り、**表示**（描画・DSP・予測・補間）を担う。公式状態の代替ではない
- **Rust NIF**: Formula バイトコードの実行に限定する

**やるべきこと**: Elixir でドメインと tick を決め、Zenoh／protobuf でクライアントへ配信する。重い式だけ Formula NIF へ。クライアントは注入された定義・フレームに従って描画する。

---

## 3. Elixir で重い連続演算をしない

**やってはいけないこと**: 行列・物理・大規模ループなど、tick 予算を食い潰す連続数値演算を Elixir で実装すること。

**理由**:

Elixir は Erlang VM（BEAM）上で動作するため、演算が他の言語と比べて遅い。1回の演算でも以下のオーバーヘッドが発生する：

```
VM命令のディスパッチ → 型チェック → ヒープから値の取得 → 演算 → 新しい値をヒープに生成 → GC対象化
```

- **ヒープベース**: すべての値がイミュータブルでヒープ上に存在し、演算のたびに新規オブジェクトが生成される
- **型の動的解決**: 実行時に型をチェックするオーバーヘッドがある
- **GC 負荷**: 計算が増えるほどヒープ割り当てが増え、GC の頻度とコストが上昇する

**やるべきこと**: 権威 tick 上のオーケストレーション・ルール分岐・状態更新は Elixir でよい。**重い式・ベクトル演算**は **Formula VM（Rust）** へ。表示用の高頻度処理はクライアント Rust へ。
