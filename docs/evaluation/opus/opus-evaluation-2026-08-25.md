## カテゴリ別の講評

### プロジェクト全体（アーキテクチャ）— +8（前回 -9）

前回マイナスのみだった大分類が初めてプラスに転じた。理由は 2 つある。1 つは「NIF をゲームロジックから撤退させた」判断の正しさが、`ResourceArc` 使用ゼロ・`unsafe` 2 箇所（どちらも OpenXR API 由来）という結果として測定可能になったこと。もう 1 つは、レイヤ逆転を config 注入・MFA 注入という**単一のパターン**で横断的に解消したことで、設計の一貫性が読み手に予測可能になったこと。

残るマイナスはいずれも「未着手」であり「壊れている」ではない。フル連合（-2）、認証の既定オフ（-1）、永続化の未配線（-1）。合計 -4 は、掲げているビジョンの大きさに対しては小さすぎる数字にも見えるが、これは「できていないことを未実装と正直に書いている」ことの反映でもある。

### auth — +53（前回 +48）

コードは 3.5 週間まったく変わっていない。それでもこの点数を維持できるのは、RS256 マルチ鍵 JWKS・refresh ローテーション + family 再利用検知・Argon2id + タイミング攻撃対策・12 バケットの多軸レート制限という中核が、商用の認証サービスと比較して遜色ない水準にあるからである。107 件のテストも要所に集まっている。

弱点も 3.5 週間動いていない。最大の問題はメール検証フローを丁寧に作りながら `login/3` がそれを見ないこと（-2）で、これは「機能はあるがゲートが繋がっていない」典型である。`/health` の DB 疎通なし、`account_tokens` の GC なし、CORS 未設定、Dialyzer / hex.audit なしは、いずれも 1 行〜数十行で埋まる項目が放置されている状態である。

### assets — +7（新規対象）

初回コミットの時点でパスポリシー・所有権の二重強制・JWKS 検証・Docker Compose・CI・release を揃えており、骨格の作り方として正しい。パスの正規化とトラバーサル拒否を独立モジュール + 専用テストにしているのは、BLOB を受けるサービスで最初に壊れる箇所を理解している証拠である。

一方でこのサービスは **18 日間、誰からも呼ばれていない**。engine 側の `__save__` / `__load__` は依然「local persistence disabled; network TBD」のログを出すだけである（-1）。書き込みのレート制限とクォータもない（-1）。「作った分だけ運用対象が増えたが価値は生んでいない」状態で、engine 側の配線 1 本が最優先である。

### engine — apps/core — +20（前回 +11）

前回 -10 だったマイナスが -4 になった。`Core.Config` の `@default_content` 撤去、`StressMonitor` の `wave_label/1` 撤去、`Stats` の汎用カウンタ化、`FrameCache` の room_id キー化と `:physics_ms` のみ必須という契約整理により、「エンジン層にゲームの語彙が漏れている」という前回最大の指摘がほぼ解消した。しかも `refute Map.has_key?(summary, :kills_by_enemy)` のようなテストで、語彙が戻らないよう凍結されている。

残るのは `Core.Telemetry` のメトリクス定義（`game.tick.enemy_count` 等、-1）、`NifBridge.Behaviour` が定義だけで注入されていないためモック不能（-2）、そして `Core.Component` の moduledoc が撤去済みの 60Hz 物理ループを説明している点（新規 -1）である。最後の 1 件は些細だが、moduledoc の誠実さをこのプロジェクトの強み（+3）として評価している立場からは、中心ビヘイビアの記述ずれは目立つ。

### engine — apps/contents — +24（前回 +6）

差分 +18 はこのカテゴリが最大級である。非 `:main` ルームでのループ駆動（前回 -4）が解消し、Zenoh publish が MFA 注入になり（前回 -2 が -1 へ）、いずれもテストで固定された。バックプレッシャー設計（throttle 時に副作用だけ落として権威更新は続ける）は依然としてこのプロジェクトで最も上手い設計判断の 1 つである。

課題はテスト密度で、lib 126 ファイルに対しテスト 8 ファイル（6.3%）。`nodes/` の 40+ モジュール、各コンテンツの playing ロジック、`FrameEncoder` の DrawCommand 変換が無検証である（-2）。`FrameEncoder` は入出力が純関数に近く golden fixture が効く対象なので、ここは費用対効果が高い。

### engine — apps/network — +22（前回 +4）

差分 +18。zlib 展開上限・セッション淘汰・JWKS 検証・S2S という 4 つの新規実装がいずれもテスト付きで入り、102 件のテスト（umbrella の 180 件中）を持つ最も厚い層になった。

残る問題は 3 種類ある。第 1 に認証の既定がオフである（-1 × 2）。第 2 に UDP の素朴な flood 耐性がない（新規 -2）。パケット長上限・セッション数上限・レート制限がなく、zip bomb を潰した後に残った単純な増幅面がそのままである。第 3 に `find_room_node` の全ノード RPC スキャン（-2）で、コード内コメント自身が改善余地を認めている。

特に指摘しておきたいのは、封筒形式（`<<len::16, token, payload>>`）の判別をヒューリスティックで行っている点（新規 -1）である。トークン検証が失敗した際に `len > 30` と Base64URL 文字種の正規表現で「封筒だったのか生 protobuf だったのか」を推測しており、条件が偶然噛み合えばペイロード先頭が黙って切り落とされる。「ワイヤの SSoT は経路・形式ごとに定める」と掲げるプロジェクトが、ワイヤの解釈を確率に委ねているのは原則違反である。マジックバイト 1 つで消える問題なので、優先して直すべきだと考える。

### engine — apps/server — +2（前回 +2）

変化なし。2 モジュール 41 行に責務を絞り、content 未設定と `:main` ルーム起動失敗の双方で `raise` する fail-fast は良い。ただしその起動シーケンスが**テスト 0 件**である（-1）。`releases:` 定義がなく配布形態が `mix run --no-halt` のみという点も動いていない（-1）。auth と assets が Dockerfile + release を持つだけに、engine だけが取り残されている。

### engine — rust/nif — +11（前回 +2）

差分 +9 のうち大半は前回マイナスの解消である。`binary_div` の型誤判定バグ（-3）、Rust 単体テストゼロ（-3）、`i32::MIN / -1` の panic（-2）がすべて解消し、修正理由がコメントとテスト名で残されている。エラーを NIF 層とドメイン層の 2 段に分ける設計は依然として堅い。

残るのは命令数・入力サイズの上限がなく `DirtyCpu` も未指定という点（-1）と、テストが除算に偏っている点（-1）である。前者は制御フロー命令を足す**前に**入れるべき順序の問題として重要で、提案側にも gas メータリングとして挙げた。

### engine — rust/client — +31（前回 +10）

差分 +21 で全カテゴリ最大。`SnapshotInterpolator` は今回唯一の +5 である。適応遅延バッファ（EMA で到着間隔を追従、80〜250ms にクランプ）、バースト到着の検出、インデックスではなく距離による近傍マッチ、新規スポーンの非表示と デスポーンの維持——素朴な lerp が必ず踏む罠を設計で回避し、18 件のテストで固定している。テスト名がそのまま仕様書になっている点も含めて、商用ネットコードの論点をこの粒度で扱った個人プロジェクトはまず見ない。Zenoh 側の publisher キャッシュ + 指数バックオフ再接続（+4）も、前回指摘への回答として周辺の細部まで仕上がっている。

一方でこのカテゴリはマイナスも最大（-14）である。OpenXR は 331 行の実装があるのに app に配線されておらず optional feature のまま、`XR_MND_headless` 必須で事実上 Monado 限定（-3）。クライアント側 52 件のテストが CI で実行されない（-3、`ci.yml:50-51` は `-p nif` のみ）。render クレート 2650 行にテスト 0 件（-2）。WASM プラットフォームは全メソッドが未実装を返すスタブ（-2）。予測未配線（-2）。`RenderFrame` の毎フレーム clone（-1）。カリング・SE ボイス上限なし（-1）。

つまり「書いたコードの質は高いが、書いたコードが使われる経路に繋がっていない」ものが集中している。`-p nif` を `--workspace` に変える 1 行で 52 件のテストが回帰検出に使われ始める、という状態が 3 週間以上続いているのは、費用対効果の観点で最も不合理な放置である。

### 横断評価層 — +18（前回 +15）

`mix alchemy.ci` が 23 秒で ALL PASSED になる状態、`proto-verify` による生成物ドリフト検出、複合アクションによる CI セットアップの共通化、`workspace/` のレーン運用、そして評価サイクル自体の制度化は、いずれも同規模のプロジェクトの平均を明確に上回る。

弱点は 3 つに集約される。第 1 に **`docs/warranty/ci.md` の陳腐化**（-2）。品質保証を説明する文書が `cargo test -p physics`（クレートは撤去済み）と `cargo bench -p physics`（ジョブは存在しない）を掲載し、`CyclomaticComplexity` を「本プロジェクト 15」と書くが `.credo.exs:9` は 10、`AliasUsage` を「3 回以上」と書くが実際は無効化、実在する `proto-verify` ジョブは未記載である。README の「main のみ `cargo bench` のリグレッション検知」も事実でない。第 2 に **CI 無効化と再有効化の反復**（-1）。現状は緑だが、`git log --follow -- .github/workflows/ci.yml` を数えると無効化側（`ci ignore`）が 6 件・再有効化側が 3 件以上あり、再発を防ぐ制度（branch protection の required checks、無効化時の文書同時更新）はゼロである。第 3 に **プロパティベーステスト・fuzz・ベンチマークの全体不在**（-2）。バイトコード VM・バイナリプロトコル・グラフコンパイラ・スナップショット補間という「ランダム入力と時間軸に晒される層」を 4 つ持つ構成に対して、example-based のみは防御が薄い。

加えて今回から採点した **ゲームプレイ完成度**（-2）は、このプロジェクトで最も目立つ非対称である。開始 → プレイ → 終了 → リトライが閉じているのは `Content.Tetris` のみで、既定に近い `BulletHell3D` はタイトル画面なし・敵 1 種・プレイヤーの攻撃手段なし・単一アリーナ。エンジンの土台の精度に対して、その上に載る遊びの量が明確に足りていない。

## 最も評価する 5 点

1. **`SnapshotInterpolator`（+5）** — 適応遅延・近傍マッチ・バースト保護を 18 テストで固定。商用ネットコードの論点をこの粒度で扱っている。
2. **RS256 マルチ鍵 JWKS + refresh family 再利用検知（+5 × 2、auth）** — 鍵ローテーション中も検証が継続でき、盗用は family ごと切る。OAuth 2.1 の推奨をそのまま実装している。
3. **NIF をゲームロジックから撤退させた判断（+4）** — SIMD 物理という武器を捨てて、ロック競合と GC 連動ライフタイムという NIF 最大の危険源を構造ごと消した。結果が `ResourceArc` ゼロ・`unsafe` 2 箇所として測定できる。
4. **golden E2E protobuf 契約テスト（+4）** — Elixir が生成した実バイト列を Rust でデコードして検証し、CI の `proto-verify` で生成物のドリフトも潰す。言語境界の契約を 3 点で固定している。
5. **`mix alchemy.ci` の単一エントリ（+4）** — 23 秒で Rust / Elixir 全チェックが回る。速いから実際に使える、という DX の本質を押さえている。

## 最も重い 5 点

1. **クライアント Rust の 52 テストが CI で実行されない（-3）** — `-p nif` を `--workspace` に変える 1 行。良いテストを書きながら使っていない状態が 3 週間以上続いている。**最も安く直せる最大の穴**。
2. **OpenXR が app に未配線・ランタイム限定（-3）** — 331 行の実装があるのに VR は動かない。「動く経路が 1 本ある」状態にしないと、実装量が増えても価値命題は動かない。
3. **UDP に生パケットサイズ・セッション数・送信頻度の上限がない（-2）** — zip bomb を潰した後に残った素朴な flood がそのまま増幅面になる。送信元詐称が容易な経路として優先度が高い。
4. **`docs/warranty/ci.md` の陳腐化（-2）** — 品質保証を説明する文書が撤去済みクレートと実在しない設定値を記述している。ドキュメント品質がこのプロジェクトの強みだからこそ目立つ。
5. **封筒形式のヒューリスティック判別（-1、重要度は点数以上）** — ワイヤの解釈を確率的推測に委ねている。マジックバイト 1 つで消える問題であり、静かにペイロードが壊れる種類のバグは発見が最も遅れる。

## 結論

**総合 +188**（プラス +257 / マイナス -69。前回 +89）。前回からの実質改善は約 +70 で、残りは評価範囲の拡大と粒度見直しによる。

このプロジェクトの現在地は「エンジンの土台は同種の個人プロジェクトの水準を明確に超えたが、土台の上に載るもの（遊び・VR・永続化・連合）がまだ薄い」である。3.5 週間の作業は前回指摘のほぼ全域に届いており、しかも直した箇所がテストで凍結されている。この循環が回っている限り、技術評価層のスコアは今後も上がると見る。

一方で今回明確になった構造的な問題は、**「良いものを書いてから、それを使う経路に繋げるまでの間が長い」**ことである。補間器は 18 テスト付きで書かれたのに CI で回らない。OpenXR は 296 行書かれたのに app から呼ばれない。assets は一式揃ったのに 18 日間呼ばれない。予測は関数が定義されたまま入力を返すだけ。これらはすべて「実装が足りない」のではなく「配線が足りない」問題で、費用は小さいのに価値の差は大きい。

次の 1 サイクルで優先すべきは、新機能ではなく配線だと考える。具体的には (1) `cargo test --workspace` の 1 行、(2) engine → assets の `__save__` / `__load__` 1 経路、(3) OpenXR の app 配線とフォールバック、(4) `docs/warranty/ci.md` の実態への追従。この 4 つはいずれも当日〜数日規模で、合計 -9 相当のマイナスを消しつつ、既に書かれた実装の価値を有効化する。

その次に、UDP の flood 耐性と封筒形式のマジックバイトというネットワークの硬さ、そして既定コンテンツを「完結したループ」にするというプロダクトの見え方が来る。
