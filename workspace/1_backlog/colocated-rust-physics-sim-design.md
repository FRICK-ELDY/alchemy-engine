# 方針: 低遅延の隣の Rust sim（サーバー物理）

> 作成日: 2026-07-23  
> ステータス: **採用方針**（実装未着手。詳細設計・スパイク後に `2_todo` 化）  
> 目的: 本格的なサーバー側物理演算を、BEAM のライブネスと Elixir 主時間（権威 tick）を守りながら導入する構成を固定する。

[← README](./README.md)

---

## 1. 採用する構成（要約）

**同じマシンで物理だけを計算する Rust 子プロセスを、Elixir ルームが監督し、内部は高速に回しても公式の確定は Elixir の主時間で行う。**

| 役割 | 担い手 | 内容 |
|:---|:---|:---|
| **主時間・権威** | Elixir（ルーム / contents） | 公式 tick（推奨 20Hz。設定で 10/30/非推奨 60）。入力の採否・順序。公式状態のコミット |
| **物理計算** | **隣の Rust sim プロセス** | 連続シム（内部 60〜120Hz 等でも可）。世界 SoA の保持。衝突などの演算 |
| **表示** | Rust クライアント | 描画・予測・補間。公式物理の真実にはならない |

```
┌─ 同一ホスト / 同一デプロイ単位 ─────────────────────┐
│  Elixir ルーム GenServer（権威 tick）                 │
│       │ 受理済み入力・定義注入・step / コミット指示     │
│       │ イベント・要約状態の取り込み                    │
│       ▼                                              │
│  Rust sim プロセス（物理ループ・世界状態の実体）         │
└──────────────────────────────────────────────────────┘
              │ Zenoh 等（既存のクライアント経路）
              ▼
         クライアント（描画・予測）
```

正本の主時間方針: [authoritative-state-sync-policy.md](../../docs/architecture/authoritative-state-sync-policy.md)

## 2. 採用しない／後回しにする選択肢

| 選択肢 | 扱い | 理由 |
|:---|:---|:---|
| 旧型 **常駐 NIF `GameWorld` 60Hz ループ** の再導入 | **採用しない** | スケジューラ圧迫・巨大境界・権威の曖昧化。一度撤去済み |
| Dirty NIF / Formula 拡張のみ | 軽い式・限定計算には可。**本格連続物理の本命にしない** | 短時間オフロード向き |
| **HTTP / gRPC 物理マイクロサービス** を第一選択 | **採用しない**（大規模化後の選択肢として記録） | レイテンシ・運用・権威境界が重い。初期の「隣」より遠い |
| クライアントを公式物理の実行主体にする | **採用しない** | チート・不一致。予測・演出のみクライアント可 |
| contents 全体を Rust Web サーバーへ移す | **本方針ではしない** | 連合・OTP 隔離・Elixir 主時間の価値命題と衝突しやすい |

## 3. 時間と権威の契約（必須）

二重の真実を作らない。

1. **公式位置・ヒット・スコア等**は、Elixir がコミットしたものだけが正である。  
2. Rust sim の内部状態は **候補／先行計算** である。  
3. Rust の内部ステップ Hz と Elixir 権威 tick は独立してよい。  
4. クライアントは sim に直接つながない（またはつながっても **表示用のみ**）。  
5. ロールバック／和解が必要なら、**input seq** と **tick id** で手順を決める（詳細は実装設計時）。

典型フロー:

1. クライアント入力 → Elixir が受理・順序付け  
2. Elixir → Rust sim: 受理済み入力の適用指示  
3. Rust: 内部で物理ステップを進める  
4. Elixir 権威 tick: 結果・イベントを取り込み **公式コミット**  
5. 公式状態から（必要なら）RenderFrame 等をクライアントへ配信

## 4. プロセスのつなぎ方（A〜D）

いずれも「隣の Rust sim」の配線候補。遅延・結合・運用のトレードオフが異なる。

### A. OS Port（`Port.open`）— 第一候補

| 項目 | 内容 |
|:---|:---|
| 概要 | Elixir が子プロセスとして Rust sim を起動。stdin/stdout または専用 fd でフレーム／メッセージをやり取り |
| プロトコル案 | protobuf（alchemy-protocol 系）または長さ付きバイナリ |
| 利点 | OTP らしい監視・終了検知。クラッシュ隔離。実装の第一歩として単純 |
| 欠点 | 大きな世界の全コピーは避ける設計が必要。Windows / Unix で起動パスの差 |
| 向く段階 | **スパイク〜初期実装の推奨** |

### B. Unix Domain Socket / localhost TCP

| 項目 | 内容 |
|:---|:---|
| 概要 | 起動済み（または Port 起動後）の sim にソケット接続 |
| 利点 | デバッグしやすい。常駐ワーカーや再接続のモデルに合う |
| 欠点 | Port より「誰がいつ listen するか」の運用が増える。TCP ならわずかにオーバーヘッド |
| 向く段階 | 常駐プール、複数ルームで 1 sim を共有し始めるとき |

### C. 共有メモリ + 通知（セマフォ / eventfd 等）

| 項目 | 内容 |
|:---|:---|
| 概要 | 巨大 SoA をコピーせず、共有領域のバージョン付きバッファを Elixir／Rust が合意して読む |
| 利点 | コピー带宽を抑えられる。最速寄り |
| 欠点 | 所有権・バースト書き込み・クラッシュ後の復旧が難しい。実装コスト高 |
| 向く段階 | **計測でコピーがボトルネックと判明してから**。初期は採用しない |

### D. 既存 Zenoh をローカルでも使う

| 項目 | 内容 |
|:---|:---|
| 概要 | ルームローカルでも `game/room/{id}/sim/...` のようなトピックで Elixir ↔ sim を接続 |
| 利点 | クライアント経路と概念を揃えられる。将来ノード分離時にプロトコル再利用しやすい |
| 欠点 | 「隣」専用としてはやや重い。トピック設計・権限・ループバック運用が増える |
| 向く段階 | リモート部屋と同じ契約に揃えたい、または既に Zenoh 必須の配備 |

### つなぎ方の選定メモ

| フェーズ | 推奨 |
|:---|:---|
| スパイク / MVP | **A（Port）** |
| 常駐・再接続が必要 | **B**（A で起動し B で接続、のハイブリッドも可） |
| コピーがボトルネック | **C** を検討 |
| 経路一本化・将来のノード分離を優先 | **D** を検討（A/B と併用も可） |

## 5. やり取りするデータ（方針）

| 方向 | 例 | 頻度の目安 |
|:---|:---|:---|
| Elixir → Rust | 受理済み入力、スポーン／デスポーン、コリジョン定義の参照、パラメータ | 入力は高頻度可。定義変更は低頻度 |
| Rust → Elixir | 衝突・ダメージ候補、要約ポーズ、完了した内部 tick / シーケンス | 権威 tick に合わせる、またはイベント駆動 |
| Elixir → クライアント | 公式状態／描画意図（既存 RenderFrame 等） | 権威 tick |

原則:

- **世界の実体は Rust sim が保持**する  
- Elixir は **イベントと要約**を取り込み公式化する  
- 毎 tick の巨大世界の Elixir ヒープコピーは避ける（旧 NIF シリアライズ問題の再発防止）

描画との関係（将来選択）:

1. Elixir が公式ポーズから DrawCommand を組む（現行延長）  
2. Rust sim が描画用要約も出し、Elixir は検証・コミット・配信に寄せる（エンティティ増向け）

## 6. ライフサイクル

初期の安全策: **1 ルーム = 1 sim プロセス**。

```
Room 起動
  → Supervisor が Rust sim を起動（A: Port 推奨。room_id 付き）
  → 初期ワールド定義を注入
Room 運転
  → 入力 flush → sim step 指示 → 結果取り込み → 公式コミット
Room 終了 / sim クラッシュ
  → down を検知 → 再起動、またはルームを安全に終了
  → 再 hydrate する場合は最後の公式スナップショットから
```

後段オプション: N ルームで 1 ワーカー（効率↑、障害影響と公平スケジューリングが難）。初期は採用しない。

---

## 7. 失敗時の方針（概要）

| 事象 | 方針例 |
|:---|:---|
| sim が重い | Elixir はバックプレッシャー（入力間引き・tick スキップ）。sim は最新入力優先 |
| sim クラッシュ | 再起動 or ルーム終了。公式スナップショットから再構成 |
| Elixir が遅い | 公式コミット遅延。sim はバッファ上限で古いステップを捨てる |
| 予測との食い違い | tick id / input seq でクライアント側を矯正 |

---

## 8. 段階的導入

1. **契約固定**: メッセージ型、tick id、コミット境界、クライアント非接続  
2. **No-op sim**: 位置エコー程度で A（Port）経路を通す  
3. **単純衝突**を sim に載せる  
4. 計測（遅延、コピー量、クラッシュ復旧）  
5. 必要なら B/C/D や描画要約の最適化  

軽い式は当面 **Formula NIF** のままでよい。連続世界シムと役割を分ける。
